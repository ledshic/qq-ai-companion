# 事件记忆、关注事项与主动决策设计

日期：2026-10-26。状态：下一版设计，尚未实施。读者：本仓库开发与维护者。

进度：第一阶段的存储、提取、更正与 observe 已实现并启用，实际边界和验证见[观察阶段实施记录](EVENT-MEMORY-OBSERVE.md)。本设计中的主动发送部分仍未开放。

架构更正：下文按休假建立专用结构的部分为历史草案，已被[参考文本驱动的通用事件模型](EVENT-REFERENCE-MODEL.md)替代，不得据此重新实现主题专用逻辑。主题语义保存在参考文本，当前实现只使用通用事件协议。

## 目标与首版范围

让小鲸鱼记住有来源的生活事件，在后续出现合适机会时自然提起。例如周五明确说“明天开始休两天，周一上班”，周一本人在群里出现后，可以择机聊复工。程序确定事实、时机和发送资格，模型负责理解与表达。

下一版先支持本人陈述的休假事件及“假期结束后关心近况”这一类关注事项。明确称呼、主动联系与调侃偏好一并支持。旅行、考试、项目进展后续沿用接口扩展，不同时加入通用自主规划、情绪数值和向量数据库。

本方案承接[人格首版实施记录](PERSONALITY-IMPLEMENTATION.md)，沿用语境观察、规则决策和只读表达计划。它是后续实现的主规格；以下默认值均为拟议值，不是当前配置。团队记忆工具本轮未提供，现状依据为本仓库源码。

## 当前实现与改动依据

| 位置 | 当前行为 | 本版补充 |
|---|---|---|
| `memory.ts`、`store.ts` | 按群和用户保存已确认发送的对话；默认 9 轮、30 分钟失效 | 独立事件与偏好存储，不能通过延长会话历史代替 |
| `GroupContext.add` | 去重、保留短期群讨论；去重记录在内存且有容量限制 | 持久化输入去重与事件来源；未回复的消息也可形成事件 |
| `Conversation.handle`、`dispatch` | 收消息、确定呼叫/接续/插话，任务按用户取消 | 输入记忆支线独立于本轮是否回复；复用原始消息身份与取消版本 |
| `Conversation.tick`、`warmUp` | 依赖暖场开关、时间段、概率与近期群消息 | 新增关注事项扫描；不能依赖旧暖场概率才能触发 |
| `PersonalityRuntime` | 按本轮输入形成表达计划，无跨轮人格状态 | 接收可信主动话题和已固定的表达倾向，不管理事件数据库 |
| `napcat-client.ts`、`delivery.ts` | 发送回调主要返回布尔值/已送达文本；按群排队 | 为主动任务增加结构化发送结果，持久化发送前标记与确认结果 |
| `lastAuto`、`hourly`、`lastWarmup` | 多数预算计数在内存中，重启不能完整恢复 | 统一主动发送预算与持久化预留，避免新路径另有一套额度 |

## 示例与事实强度

以下为匿名合成场景，时区均为 Asia/Shanghai。

| 输入与时间 | 能保存的事实 | 2026-10-26 的可用话题 |
|---|---|---|
| 10 月 23 日：“明天开始休两天，周一上班” | 假期覆盖 24、25 日；本人明确说 26 日复工 | 可以说“今天开工了”，但不声称实际打卡或到岗 |
| 10 月 23 日：“明天开始休两天” | 假期覆盖 24、25 日；未说明下一次上班日 | 可以提“这两天假结束了”，或问“今天上班吗”，不能推断周一必上班 |
| 上周：“放两天假” | 有两天休假的陈述；开始和结束未知 | 首版只在本人再次聊假期时召回，不自动生成今天复工候选 |
| “要是能放两天假就好了” | 愿望，非已经确定的休假 | 不创建可触发的休假事件 |
| “他说他放两天假” | 第三方转述 | 首版不保存为说话人本人的休假 |
| 后续：“改了，下周才休” | 原计划被更正，日期可能仍待明确 | 停止旧关注事项，不继续按旧日期问候 |

自然日区间采用开始包含、结束不包含。例如 24、25 日休假记为 `[2026-10-24, 2026-10-26)`。涉及工作日、轮班或跨时区时，不从自然日假期结束自动推算返岗日。

## 总体处理流程

```mermaid
flowchart LR
  A[接收有来源的发言] --> B[提取并校验事件与偏好]
  B --> C[保存记忆与关注事项]
  C --> D[时间或本人出现触发检查]
  D --> E[判断本次是否合适提起]
  E --> F[按人设生成并复查]
  F --> G[发送与确认记录]
```

记忆保存不以机器人回复成功为前提。主动发送继续服从明确呼叫优先、取消、群队列和发送前时机检查；本版不建立第二个 QQ 主循环。

## 数据结构与来源约束

以下标识符仅在本地保存。模型输入沿用 `modelContext` 的匿名映射，事件与证据额外映射成当轮别名，不把数据库主键或真实账号传给模型。时间戳为 UTC 毫秒；自然日另存时区与 ISO 日期。

```ts
interface Scope {
  groupId: string;
  ownerId: string; // 被描述的人；首版本人陈述时等于消息发送者
}

interface Evidence {
  id: string;
  groupId: string;
  messageId: string;
  authorId: string;
  sourceAt: number;
  receivedAt: number;
  excerpt: string; // 最多 500 字，足以核对提取，不保存整段群聊
  scopeEpoch: number; // 清空/退出后的版本，拒绝旧任务提交
}

interface Fact<T> {
  value: T;
  basis: 'stated' | 'derived';
  evidenceIds: string[];
  rule?: 'relative-date-v1' | 'calendar-duration-v1';
}

interface VacationEvent extends Scope {
  id: string;
  version: number;
  type: 'vacation';
  status: 'active' | 'superseded' | 'retracted' | 'expired';
  // 可为空；存在时日期区间必须完整并通过时区/日历校验。
  period: Fact<{ startDate: string; endDateExclusive: string; timezone: string }> | null;
  durationDays: Fact<number> | null;
  resumeOn: Fact<{ date: string; timezone: string }> | null;
  evidenceIds: string[];
  replacesId?: string;
  createdAt: number;
  updatedAt: number;
  expiresAt: number;
  scopeEpoch: number;
}

interface ContactPreference extends Scope {
  version: number;
  proactive: 'on_presence' | 'allow_quiet' | 'off';
  banter: 'default' | 'off';
  nickname?: string;
  timezone: string;
  activeHours: [number, number];
  evidenceIds: string[];
  scopeEpoch: number;
}
```

`Fact.basis=stated` 表示用户明确陈述，不等于已发生或外部核验。模型只提出事实片段、相对时间表达和引用别名；本地代码绑定人物、来源、当前日期和版本，并执行支持的日期规则。模型不能自行填写权限、状态版本和已发送标志。

首版日期语法支持明确年月日、可确定的星期、今天/明天/后天和以自然日计的明确持续天数。星期可能有多种解释、来源时间缺失、跨时区不明、半天或工作日计数不明确时，保留未知字段，不强行创建到期任务。日期变化跨午夜时仍以原消息时间解析，不能按提取完成时刻重算。

“改期”只有在本人、同群、引用或明确语义能唯一关联旧事件时才替换。无法唯一关联时保存为待确认提议，不自动撤销多个事件，也不为每个模糊提议主动追问。用户下次相关交流时可自然确认。

## 关注事项与决策契约

事件描述过去或已经表达的事实；关注事项描述未来可能值得提起的一次机会。

```ts
type AttentionState = 'pending' | 'leased' | 'dispatching' | 'delivered'
  | 'covered' | 'uncertain' | 'cancelled' | 'expired' | 'skipped';

interface AttentionItem extends Scope {
  id: string;
  eventId: string;
  eventVersion: number;
  kind: 'vacation_followup';
  occurrenceAt: number; // 固定机会日期的本地零点对应 UTC；更正必须新建
  claimMode: 'resume_stated' | 'vacation_ended';
  notBefore: number;
  expiresAt: number;
  nextCheckAt: number;
  requiresPresence: boolean;
  state: AttentionState;
  version: number;
  scopeEpoch: number;
  tone: 'upbeat' | 'wry' | 'gentle';
  toneSeedVersion: string;
  judgmentCount: number;
  safeRetryCount: number;
  leaseToken?: string;
  leaseUntil?: number;
}

type ProactiveDecision =
  | { action: 'wait'; nextCheckAt: number; reasonCode: string }
  | { action: 'skip'; reasonCode: string }
  | { action: 'propose'; intent: 'acknowledge_resume' | 'ask_after_break';
      evidenceIds: string[]; banter: 'off' | 'light'; reasonCode: string };
```

同一有效事件首版只产生一次 `vacation_followup`。明确复工日优先使用该日；否则用明确假期结束日，`claimMode=vacation_ended` 限制为提假期结束或询问是否上班。两者都未知则不建关注事项。复工日与假期区间冲突时暂停建项，等待更正。

程序在发送资格通过后才请求模型做社交判断。模型仅建议“现在提起是否合适、是否已经讨论过”；只允许引用当前提供的事件与消息别名。无效返回、超时或不确定按 wait 处理。模型不能指定目标群、改变机会日期、扩大预算或直接发消息。

`reasonCode` 必须使用受版本管理的有限枚举，例如 outside_hours、no_presence、busy、budget、topic_conflict、already_covered、evidence_changed、uncertain、eligible。日志不使用模型随意生成的原文理由。

## 输入采集与记忆写入

| 项目 | 首版规则 |
|---|---|
| 开关与范围 | `EVENT_MEMORY_ENABLED=false` 默认关闭；只有配置允许的群可采集，`EVENT_MEMORY_SCOPE=addressed|group` 默认 addressed。group 用于记住未叫机器人的本人发言，必须显式启用 |
| 本次任务的目标配置 | 实施时为指定群启用 group 才满足“随口提过放假也能记住”；设计阶段不改实际配置 |
| 持久化入口 | 在短期讨论去重之前对原始、可验证的群消息建来源收件记录；恢复时可继续未完成的提取；没有真实消息 ID 的本地模拟数据默认不入持久库 |
| 消息范围 | 只采集实际收到的新文本，不自动翻历史或扫全群；图片、引用内容不作为本人事实；退出或清空等控制消息先处理，不入提取队列 |
| 提取调度 | 新消息按群和发送者聚合 3 秒，最多等 10 秒，最多 10 条/4000 字；消息归属分开，不按时间邻近合并不同人的事件 |
| 事件完整性 | 合并只是请求批次；每个候选必须有自己的来源和人物。重复说同一假期需合并证据，不能不断新建关注事项 |
| 模型并发 | 复用同一 `Semaphore`，新增非阻塞低优先级获取方式；背景模型任务最多 1 个，MAX_INFLIGHT≥2 时为呼叫保留至少 1 个名额；等于 1 时，明确呼叫到达会取消背景任务后取得名额。背景任务不能排长队 |
| 成本与失败 | 每群每小时最多 12 次提取请求、每次 5 秒，不自动重试同一批；预算不足在 24 小时来源保留期内延期，超出后丢弃并记录计数 |
| 提取失败 | 批次标记 failed，不把不完整结果当事实；无依据日期、人物不符和任意状态补丁均拒绝；不阻止正常聊天 |

收件去重键为 `(group_id, message_id)`。群范围和作者先由 OneBot 字段确定，模型只在该范围内提出候选。时间早于当前 24 小时的重放不自动入库，未来超过 5 分钟的时间戳不参与日期推断；需要历史导入时另设显式操作。

本人说“以后别主动找我”或“别再拿我开玩笑”可形成偏好；命令提供确定性控制：`/主动关心 开|关`、`/清空长期记忆`、扩展原 `/清空记忆`。自然语言偏好沿用同批语义提取，提交后取消相关任务，不等待机器人回答发送成功。提取未完成期间的直接停止请求仍由当前参与判断与发送前复查保护。

## 触发条件与检查顺序

新增独立的 60 秒轻量扫描，只查数据库与时间；该扫描由 Node bot 的现有生命周期管理，不创建桌面自动化。关闭 WARMUP 不影响事件扫描。收到本人消息、事件更正、偏好更新和连接恢复时，也可触发检查。

每轮依次执行以下条件，前面的失败不调用后面的模型：

1. 全局开关、群允许范围、用户偏好允许；QQ 连接就绪，事件有效，版本与 scopeEpoch 一致。
2. 到达 notBefore、未到 expiresAt，且处于配置时区的允许时段。默认 09:00–18:00；机会当天结束后过期，不第二天补发“今天开工”。
3. 默认 `on_presence`：本人在该机会日收到过至少一条新消息，并且最近 15 分钟内仍有活动。只有他人在聊不足以触发；重放旧消息不算出现。
4. 当前没有同用户呼叫/接续任务、同群待发送机器人批次或另一主动任务；群最后一条人类消息距今至少 20 秒，避免抢话。
5. 没有已完成、结果不明或被讨论覆盖的同一机会；检查持久化预算。多候选按“明确复工优先、到期更早优先、创建更早优先”排序，每群同时最多一个。
6. 在同一个不可变快照上做社交判断：已有人问候、本人已讨论复工、正在认真求助或不适合插话时，分别 covered 或 wait，不硬转话题。
7. 形成可信话题与表达计划，生成不含工具调用的单条短消息；发送前重新检查事件版本、偏好、窗口、预算与讨论变化。

本人当天发过一句、随后离开超过 15 分钟，则继续等本人新消息。`allow_quiet` 才可不要求本人出现；首版该模式仍要求本群最近 15 分钟有新活动，不支持向完全沉寂的群定时喊话。

notBefore 为目标自然日 09:00，expiresAt 为同日 18:00，均按拥有者配置时区计算；如果允许时段另有配置则取其当日区间。首版拒绝跨午夜时段，避免机会日期歧义。时区或时段变更重算未发送机会并增加版本，已发送/不明机会不得重新打开。

wait 的 nextCheckAt 由程序限为至少 5 分钟后，并受 expiresAt 限制；没有新输入或状态变化时不再次请求模型。每个关注事项每天最多 3 次社交判断，耗尽标记 skipped，不能持续扫描直到模型同意。新输入唤醒也受最小间隔与次数限制。

## 人格与随机倾向

tone 只在创建关注事项时抽取并保存，首版 upbeat、wry、gentle 等权；参数与随机种子可注入测试。重复扫描、生成失败和重启不能重新抽取。日期、事实、是否发送与权限不随机。

积极可表现为“来，先拿下一件小事”；消极仅表现为小鲸鱼自己的轻度嘴硬，例如“工位倒是挺长情，一直等你回来”。不随机指责对方、不推断对方讨厌工作，不声称机器人真的返岗。gentle 是自然关心，不额外建立亲密关系。

优先级为用户明确偏好与当前认真/困扰场景、事实强度、人格固定边界、tone。wry 遇到 banter=off 必须被压制，本次保存的倾向可留作记录，但不会强行进入台词。新主动意图使用独立 `ProactiveTopic` 输入，不能全部硬塞进目前的 warmup 本地 casual 计划。

生成上下文只包含当前群、目标用户的最多 3 条相关事件及 1 条关注事项，另附近期必要讨论。事件摘要为资料，固定指令来自代码和角色文件。默认一条、不配图、不 @、不引用上周原消息；只在最近上下文能自然识别对象且本人仍是相关话题参与者时发送，对象容易混淆则等待。

本版不预设“开工了”等固定句库。通过允许断言列表约束内容：`resume_stated` 可提“你之前说今天上班”，不能声称已到岗；`vacation_ended` 只能提假期结束/询问现状。生成后增加一次事实范围检查，拒绝把推断写成确定事实；失败时等待，不再请求模型重写。

## 去重、并发与发送结果

本方案采用“结果不明不重发”的保守策略。QQ 发送与本地数据库无法形成单一事务，不能承诺跨系统 exactly-once（恰好执行一次）。宁可漏掉一条主动问候，也不因重启重复打扰。

| 层次 | 键或机制 | 处理 |
|---|---|---|
| 来源消息 | UNIQUE(group_id, message_id) | 重连重复事件不重复提取，清空也保留无正文的短期去重标记 |
| 提取批次 | UNIQUE(batch_key)，包含来源集合与提取器版本 | 多 worker/重启不能重复处理同一批；新版本不自动重跑历史 |
| 业务事件 | 本人、类型、明确日期构成稳定 event_key | 唯一可关联时合并证据；无日期事件仅按同一来源去重，不做猜测合并 |
| 关注事项 | UNIQUE(event_id, kind, occurrence_at) | 更正增加事件版本，取消旧待发送项；重复陈述不产生第二次机会 |
| 并发任务 | 带版本比较的 leaseToken，租约 60 秒 | 事务抢占；每群一条在途主动任务；20 秒任务总期限，租约内完成，否则中止 |
| 行动 | 一个 attention_id 对应一个 logical_action_id | 保存生成计划、tone 和发送结果；确定未发送可重试但复用同一行动身份 |
| 实际发送 | 写 socket 前持久化 dispatching，随后记结果 | 一旦可能写入过 socket，重启按 uncertain 处理，不重发 |

event_key 只用于同一明确日期事实去重。修改日期必须通过关联旧事件的更正事务，不能仅创建另一个日期键而留下旧任务。已 delivered、covered 或 uncertain 的事项遇到日期更正，首版更新事件事实但不自动新增第二次主动交流。

```ts
type DeliveryOutcome =
  | { status: 'not_sent'; reason: string } // 能证明没有尝试写出
  | { status: 'confirmed'; text: string; messageIds: string[] }
  | { status: 'partial'; confirmedText: string; uncertainTail: boolean }
  | { status: 'unknown'; reason: string };

interface ActionAttempt {
  id: string;
  attentionId: string;
  attemptNo: number;
  state: 'prepared' | 'dispatching' | 'confirmed' | 'not_sent' | 'partial' | 'unknown';
  createdAt: number;
  finishedAt?: number;
  outcome?: DeliveryOutcome;
}
```

布尔发送接口保留给旧调用方，新主动路径使用 `sendDetailed`，由同一底层队列实现。`status=not_sent` 只用于写出前取消、未连接等可证明未尝试的情况。写入回调出错、超时、断开或无法证明无副作用的服务错误均归 unknown。解析出的明确服务拒绝是否可重试，首版也按 unknown 保守处理。

事务规则如下：

- 抢占关注事项时同步预留持久化主动预算；生成和判断不持有数据库写事务。预算不足直接 wait。
- 在队列内、紧邻真正发送的位置，重查版本并写 dispatching；写标记失败不得发送。若重启发现该状态，即使可能还没真正写 socket，也设 uncertain 并封住机会。
- confirmed 在事务中将关注事项置 delivered、保存确认结果、把预留额度转为消耗。partial 有任一确认内容就封住机会，不补发剩余内容；历史只保存确认文本。
- unknown 将关注事项置 uncertain，不写成已发送事实，但保留一次预算消耗。not_sent 释放预留，5 分钟后最多一次安全重试；仍受有效期和判断次数限制。
- leased 且没有 dispatching 的任务到期可回 pending，释放过期预留；尚在生成的旧 worker 必须在队列内通过租约令牌和版本检查，否则不能发送。
- ACK（服务端发送确认）已经到达但本地事务失败，持久化的 dispatching 仍阻止恢复后重发。这个窗口可能少记一次聊天，不能因此盲目补发。

这条主动消息首版强制单段、不配图。partial 类型为共享发送适配保留，也必须用注入失败测试证明不重复发送。主动成功后更新群上下文并给目标用户打开原有接续窗口，但不伪造一条“用户主动提问”写入个人历史。

当前 `followUp` 在个人 history 为空且非 awaitingReply 时直接退出，需要显式增加“有效窗口关联最近已确认的定向主动行动”这一例外。该关联包含 actionId、目标、确认文本与时间，只允许同群本人在有效窗口内使用；模型据群上下文与确认文本判断，不把机器人发言冒充 user 历史。unknown 不打开窗口；跨重启只在确认记录仍在原窗口期限内时恢复，不续期。下一个真实用户回复成功后，再按原规则记录实际问答。

## 预算、优先级与持久化

共同预算覆盖事件关心、语义主动插话与旧暖场：沿用 AUTO_REPLY 的群冷却及小时上限，新增持久化计数与预留。明确呼叫、正常接续不消耗主动预算，始终优先。旧概率暖场在有合适事件候选时让位，不同时排队两条开场。

事件关心另有限额：每人每天最多 1 条、每群每天最多 2 条。unknown 与 partial 同样占用；not_sent 不占用。同群多个候选共享事务预留，不能先分别通过检查再一起超额发送。重启、断开和改配置不清空当天已消耗额度。

SQLite 继续使用现有数据库文件，独立 `EventStore` 管理新表。迁移使用单独 `event_schema_version`，避免占用旧会话库未知的通用版本；启动在事务中逐级迁移。旧 sessions 表与 ConversationMemory 行为保持兼容，关闭功能不删除新数据。

| 新表 | 主要约束与索引 |
|---|---|
| event_inbox / event_batches | 来源复合唯一键、批次唯一键；待处理时间索引；只在提取保留期内保存原文 |
| event_evidence / event_memories | 外键关联来源；事件行 version、scope_epoch；按群/用户/有效期检索 |
| contact_preferences / scope_epochs | 群与拥有者复合主键；清空和退出递增版本 |
| attention_items | 机会唯一键；按 state、next_check_at、expires_at 索引；保存 tone |
| proactive_actions / action_attempts | attention_id 对逻辑行动唯一；(action_id, attempt_no) 唯一；写出前状态持久化 |
| proactive_budget / budget_reservations | 群小时、用户日、群日等窗口键；每行动一次预留，不因重查多次占额 |

新表初始化或写入失败时关闭事件记忆与该主动路径，保留普通聊天，日志明确显示 disabled/error，不能显示已启用。所有写入遵循单一事务顺序，避免两个连接互相持锁调用；关闭时停止新任务、取消模型请求，再关闭存储。

## 更正、清空与保留期限

| 操作 | 行为 |
|---|---|
| `/清空长期记忆` | 删除本群该用户事件、证据、偏好正文和关注事项，递增 scopeEpoch，取消在途任务；偏好恢复默认 on_presence。发送审计仅保留去重所需无正文状态 |
| `/清空记忆` | 同时执行原个人历史清空与上述长期清空；从本群短期快照移除该用户旧发言和相关定向机器人记录，防止马上从旧上下文召回；不宣称清除模型服务商记录 |
| `/主动关心 关` | 保存 off 偏好并取消待发任务，已有事件不删除；重新开启时不补发已过期或旧计划，后续本人新交流才生成可用候选 |
| 本人更正/撤回 | 更正事务更新版本并取消旧机会；消息撤回需接入实际 notice，无法取得撤回来源时不声称能自动删除 |
| 清空与发送竞态 | dispatching 前版本变化可拦截；已经写出无法撤回保证，记录真实结果，不再次生成。所有迟到提取结果用旧 scopeEpoch 提交均失败 |

建议初始期限：原文收件箱 24 小时；事件与必要证据最多 30 天；待确认提议 7 天；无正文去重/行动状态 30 天；off 和明确调侃偏好持续到本人更改或清空。超过收件时间范围的旧消息不重新提取，避免去重清理后复活旧事件。

只为到期日在事件保留期内的事件创建可发送事项；更远日期先保留事实，不承诺自动追踪。当天事实已到期也不能为了等待本人出现自动延长到下一天。

容量起点：每群最多 200 条有效事件、每用户最多 20 条、每群最多 100 条待处理来源。先清过期内容；仍满则拒绝新候选并记录统计，不驱逐尚在发送的行动记录。事件删除、证据清理和去重保留分开执行，不因清理内容重新开放旧机会。

本版不导入过去已经失效的 30 分钟历史，也不声称记得启用前上周的发言。需要导入某条历史时，由明确操作提供来源及原始时间，单独评估后实现。

## 验收标准

程序测试使用假时钟、可注入随机数、固定模型观察和模拟发送结果；每个用例同时断言动作、状态、调用次数和额度，不能只看最终台词。真实模型测试使用匿名合成输入，不向 QQ 群投放测试消息。

| 编号 | 情境 | 必须通过的结果 |
|---|---|---|
| E01 | 周五“明天休两天，周一上班” | 解析为正确日期和时区；只生成周一一条机会；依据可追溯 |
| E02 | 只说“明天休两天” | 不生成已确定复工事实；只能提结束或询问 |
| E03 | “放两天假”、愿望、第三方转述、引文 | 不强行确定日期或人物；不产生今天复工断言 |
| E04 | 原消息跨午夜才提取 | 按 sourceAt 计算；改变宿主时区不改变事件日期 |
| E05 | 未 @、机器人未回复，但 group 采集已开启 | 仍形成本人事件；addressed 模式下同一消息不入库 |
| E06 | 重复消息、分片、重复陈述、重启重放 | 来源只处理一次；同一明确事件合并证据；同一机会只一条 |
| E07 | 更正日期与旧任务正在生成 | 旧任务不能发送；新日期未到不触发；已完成/不明机会不重新打开 |
| E08 | 周一其他人在聊，本人未出现 | 不发送；本人当天出现后才有资格，超过 15 分钟又等待 |
| E09 | 安静时段、机会过期、断线到第二天才恢复 | 不发送；不补发过时“今天开工” |
| E10 | 本人已说“今天开工了”，或他人已充分问候 | covered，取消本轮计划；不再重复关心同一机会 |
| E11 | 本人认真求助、多人话题对象不清 | wait；不为消耗候选插话；无新状态时不重复请求模型 |
| E12 | 多候选、两个扫描同时运行 | 同群仅一个租约；持久化预留不超群小时/群日/用户日限额 |
| E13 | 重启、重复扫描、一次 not_sent 安全重试 | tone 不重抽；机会 ID 不变；额度不重复占用；最多一次重试 |
| E14 | 生成期间新的明确呼叫 | 主动任务让位，不能卡住呼叫；旧草稿不再发送 |
| E15 | 模型无效 JSON、假证据、错误人物、超时 | 不入事实库或不发送；正常聊天可用；JSON 模式请求必须满足实际提供方要求 |
| E16 | socket 未写前取消/断开 | not_sent，释放额度；不记录为已发送 |
| E17 | 已写出但 ACK 丢失，随后重启 | uncertain，机会不重发，保留预算消耗，不声称确认送达 |
| E18 | 写 dispatching 后、socket 写出前崩溃 | 恢复后保守封住机会，不重复发；承认可漏发 |
| E19 | ACK 到达后数据库提交失败 | 原 dispatching 仍阻止重复；不得通过自动重试制造第二条 |
| E20 | 已确认第一段，第二段失败/不明的适配测试 | partial 封住机会；历史仅含确认文本；不补发尾段 |
| E21 | 清空/关闭时提取或生成仍在运行 | 旧 epoch 不能提交；旧计划发送前被拦；清空后不能从旧短期快照立即恢复 |
| E22 | A/B 同群并发、同一人在不同群 | 事件、偏好与证据不串用；scope 未提供的内容不发给模型 |
| E23 | wry 倾向遇到停止调侃或困扰 | 不嘲讽；事实和人设稳定；不得将随机态度描述为用户真实情绪 |
| E24 | 切回关闭模式、新表不可用或迁移失败 | 原聊天与原记忆可用；主动路径明确停用；回退无需删除数据库 |
| E25 | 成功发送后用户回复 | 群上下文记录真实发送，能进入现有接续流程；不存在虚构的用户历史输入 |

模型验收固定 30 组匿名上下文，每组运行 3 次，覆盖上述时间强度、多人归属、认真/玩笑转换和主动时机。先由人工标注允许提取的事实、允许说法与合适动作；保留模型版本、提示版本和结果。

进入试运行的最低标准：程序用例全部通过；90 个模型样本中无串群、无虚构明确日期、无把未确认复工写成已经到岗的错误；事实提取及主动动作与标注一致率分别至少 90%。语气由人工检查符合小鲸鱼设定且无明显冒犯。样本只用于进入试运行，不证明长期错误率为零。

社交判断与事实检查分别最多 3 秒、独立生成最多 8 秒，均不自动重试；单主动任务总期限 20 秒。记录真实超时比例，成功样本不能掩盖回退比例。原明确呼叫的既有测试通过，并以并发压测确认背景任务不会抢占其可用名额。

## 实施顺序与发布条件

1. 先实现存储、提取和更正，在 observe 模式运行：只保存事件与候选，不主动发送。核对假期时间和来源，完成清空与恢复测试。
2. 增加结构化发送适配、写出前记录与持久化预算，先跑故障注入和跨重启回放，通过 E12–E21 后才接通真实主动发送。
3. 为允许群启用 on_presence；首轮只开放 vacation_followup、单条文字、无工具与配图。模型验收通过后再试运行，记录误提、重复、被忽略和用户明确反馈。
4. 是否开放 allow_quiet、其他事件类型和更多主动动作另行评估，不能因模型认为有趣就自动扩大范围。

建议配置为 `EVENT_MEMORY_ENABLED`、`EVENT_MEMORY_GROUPS`、`EVENT_MEMORY_SCOPE` 和 `EVENT_FOLLOWUP_MODE=off|observe|on_presence`。默认全部关闭；进入试运行时必须同时确认采集群范围与发送模式，不能把“已保存事件”等同于“允许主动发言”。
